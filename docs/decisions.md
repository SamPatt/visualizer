# Decisions to make before writing code

Each of these changes what gets built. They are ordered by how much they
constrain everything downstream. Recommendations are given, but they are
opinions, not conclusions.

## 1. Where does the flow come from — static or recorded?

"Show a flow moving through the code" has two very different readings.

**Static.** Parse the source, build a call graph, animate a path through it.
Works on any repo without running it, including ones you cannot run. But a
static graph shows what *could* be called, and in a dynamic language it is
frequently wrong in both directions — it misses dispatch through callbacks and
invents edges that never fire.

**Recorded.** Instrument an actual run and animate the trace that really
happened. This is true by construction, and it makes `TRACE ONE STEP` mean
something exact. The cost is that the repo has to be runnable, and you need an
entry point worth tracing.

**Recommendation: recorded, with static as the fallback for structure.** The
reference's own framing — a flow you can pause a single step at a time — only
pays off if the steps are real. A trace also gives node "temperature" (how often
something is hit) for free, which is a natural fit for extrusion height.

## 2. What decides the grouping and the prose?

This is the thing that makes the reference good, and it cannot come from a
parser. The sidebar groups are `THE EVOLUTION LOOP`, `THE GAME`, `WHAT COMES
OUT` — those are *meanings*, not directories. The right-hand panel is written
explanation with judgement in it.

Three options: hand-authored in a config file, generated by a model, or
inferred from directory structure. Directory structure is the honest default and
also the least interesting; it produces exactly the diagram you could already
draw yourself.

**Recommendation: a checked-in manifest that a model can draft and a human
edits.** The manifest is the artifact — the tool reads it, the model proposes it,
you correct it. That keeps the output stable between runs, which a
model-on-every-run design would not.

## 3. Which languages, first?

"Any codebase" is the goal, not the first milestone. tree-sitter has grammars for
everything and gives a uniform tree, but call resolution is per-language work
regardless of the parser.

**Recommendation: one language end to end before a second.** Python is the
easiest to trace at runtime (`sys.setprofile`) and Sam has the most of it.

## 4. Renderer

SVG suits line art, is inspectable, and gets hit-testing and text for free.
Canvas scales further. WebGL is almost certainly overkill for a diagram whose
whole aesthetic is *restraint*.

**Recommendation: SVG until it is measurably too slow**, with the node count
capped by the manifest anyway — a map with 500 blocks on it has already failed
at its job.

## 5. Isometric layout

Placing blocks so edges route cleanly in isometric space is the hardest visual
problem here. Options: hand-placed coordinates in the manifest, a layered graph
layout (dagre/ELK) projected into isometric, or force-directed then snapped to
the grid.

**Recommendation: layered layout, projected, with manifest overrides.** The
reference clearly has a hand-tuned arrangement — the loop is a legible rectangle
— and no automatic layout will find that unaided. Let the algorithm get it 80%
there and let the manifest pin the rest.

## 6. What does extrusion height mean?

It is a data channel and the reference uses it (*"the tall structures are the
measuring parts"*). Candidates: lines of code, call frequency from the trace,
fan-in, cyclomatic complexity.

**Recommendation: call frequency**, if the flow is recorded. It is the only one
that changes between runs, which makes the diagram a picture of *this
execution* rather than of the file listing.

## 7. Output shape

A CLI that emits a single self-contained HTML file is the most portable thing —
it can be committed, attached, or served, with no runtime. The alternative is a
local server with live reload, which is nicer to develop against.

**Recommendation: single-file HTML as the product, dev server as a convenience.**

## Open question worth settling early

Is this a tool for **explaining a system to someone else**, or for
**understanding a system yourself**? The reference is clearly the former — it is
polished, curated, and written. A tool for the latter would favour completeness
and speed over prose and layout tuning. Both are good; they are not the same
program, and the manifest-heavy design above only makes sense for the first.
